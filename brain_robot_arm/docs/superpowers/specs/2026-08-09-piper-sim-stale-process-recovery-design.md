# PiPER 仿真残留进程自动恢复设计

## 1. 问题

`start_brain_robot_demo.sh` 通过独立进程组启动 `start_piper_sim.sh`。底层脚本当前会检测旧的 Gazebo、腕部相机仿真和 MoveIt2 进程，但只要发现其中任意一个就直接退出。上层清理函数只能可靠回收本次启动后记录的进程组，因此上一次清理被中断后留下的孤儿进程会使之后每次启动都失败。

## 2. 选定方案

底层仿真脚本增加“单实例锁 + 精确残留清理”。脚本先获取当前用户专用的仿真锁；获取失败表示另一套新版一键仿真仍在正常运行，此时只报错，不关闭它。获取成功后，如果发现历史遗留的项目仿真进程，则按进程组统一关闭并在确认消失后继续启动。

不采用宽泛的 `pkill ros2`、`killall python3` 或关闭所有 Gazebo/ROS2 进程。清理范围只包括本项目已知的腕部相机 Gazebo 启动进程、PiPER MoveIt2 启动进程、`gzserver` 和 `gzclient`，并排除当前启动脚本所在的进程组。

## 3. 清理顺序

1. 使用 `/tmp` 下带当前用户 UID 的锁文件，防止两个新版启动脚本并行运行。
2. 收集已知残留进程的进程组 ID，去重并排除当前进程组。
3. 向残留进程组发送 `TERM`，最多等待 8 秒。
4. 对仍未退出的残留组发送 `KILL`，再短暂等待。
5. 重新执行相同的精确检测；仍有残留则停止启动并输出 PID/命令行诊断。
6. 清理成功或本来没有残留时，继续现有 Gazebo、控制器、MoveIt2 和 RViz2 启动流程。

## 4. 安全边界

- 自动恢复仅存在于仿真启动脚本，不调用 `init_arm.sh`，不访问 CAN，也不连接实体机械臂。
- 正常持锁的新版实例不会被第二次启动关闭。
- 旧版脚本没有锁，因此第一次使用新版脚本时会被识别为历史残留并关闭；这是从旧版迁移到新版时的一次性恢复行为。
- 上层脚本现有的重复 `Ctrl+C` 防护和本次进程组清理逻辑保持不变。

## 5. 验证标准

1. `bash -n` 检查两个启动脚本均无语法错误。
2. 没有残留时，一键脚本直接进入 Gazebo 启动阶段。
3. 有旧版孤儿进程时，一键脚本显示自动清理信息，清理完成后继续启动，而不是立即退出。
4. 已有新版实例持锁时，再次启动只提示实例正在运行，不关闭原实例。
5. 一次 `Ctrl+C` 后，项目仿真进程全部退出；再次启动不再出现固定的残留错误。
